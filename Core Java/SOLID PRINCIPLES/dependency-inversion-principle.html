Dependency Inversion Principle (DIP)

Detailed Explanation with Examples – Interview Ready

1. What is the Dependency Inversion Principle?

The Dependency Inversion Principle (DIP) states:

“High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions.”

In simple terms, your business logic should not be tightly coupled to implementation details like databases, APIs, or file systems.

Key idea:
If your core logic breaks when you change a low-level class → DIP is violated.

2. Why DIP is Important

  • Reduces tight coupling
  • Makes systems flexible and extensible
  • Improves testability (mocking becomes easy)
  • Supports clean architecture
  • Allows easy replacement of implementations

3. DIP Violation Example (Wrong Design)

Problem: High-level module depends on a concrete class 
class MySQLDatabase {
    public void save(String data) {
        // save to MySQL
    }
}

class OrderService {

    private MySQLDatabase database = new MySQLDatabase();

    public void placeOrder(String order) {
        database.save(order);
    }
}

Why this is wrong:

  • OrderService is tightly coupled to MySQL
  • Switching to MongoDB requires code changes
  • Hard to write unit tests
  • Violates DIP

4. DIP Compliant Design (Correct Way)

Solution: Depend on abstractions

Step 1: Create an Abstraction

interface Database {
    void save(String data);
}

Step 2: Implement the Abstraction

class MySQLDatabase implements Database {
    public void save(String data) {
        // save to MySQL
    }
}

class MongoDatabase implements Database {
    public void save(String data) {
        // save to MongoDB
    }
}

Step 3: Inject the Dependency

class OrderService {

    private Database database;

    public OrderService(Database database) {
        this.database = database;
    }

    public void placeOrder(String order) {
        database.save(order);
    }
}

Now OrderService does not care whether data is saved to MySQL, MongoDB, or any other database.

5. DIP vs Dependency Injection (Important)

  • DIP → Design principle (what to do)
  • DI → Technique (how to do it)

Frameworks like Spring implement Dependency Injection to help you follow DIP.

6. DIP in Spring Boot (Real-World Example)

public interface PaymentGateway {
    void pay();
}
    
@Service
public class RazorpayGateway implements PaymentGateway {
    public void pay() {}
}

@Service
public class StripeGateway implements PaymentGateway {
    public void pay() {}
}
    
@Service
public class PaymentService {

    private final PaymentGateway gateway;

    public PaymentService(PaymentGateway gateway) {
        this.gateway = gateway;
    }
}

Spring injects the correct implementation at runtime. Business logic remains unchanged.

7. Common Mistakes with DIP

  • Depending directly on concrete classes
  • Confusing DIP with simply “using interfaces”
  • Creating abstractions too late
  • Hardcoding dependencies using new
Rule of thumb:
High-level policy should never know low-level details.

8. Interview-Ready Summary

The Dependency Inversion Principle ensures that business logic depends on abstractions rather than concrete implementations. This makes systems flexible, testable, and easy to extend.

9. One-Line Memory Hook

“Depend on interfaces, not implementations.”
