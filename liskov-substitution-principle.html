Liskov Substitution Principle (LSP)

Detailed Explanation with Examples – Interview Ready

1. What is the Liskov Substitution Principle?

The Liskov Substitution Principle (LSP) states:

“Objects of a superclass should be replaceable with objects of its subclasses without breaking the application.”

In simple terms, if class B is a subclass of class A, then B must behave exactly like A wherever A is used.

Key idea:
If replacing a parent object with a child object changes behavior → LSP is violated.

2. Why LSP is Important

  • Ensures reliable polymorphism
  • Prevents unexpected runtime behavior
  • Makes inheritance safe
  • Improves testability
  • Supports clean object-oriented design

3. Classic LSP Violation (Rectangle–Square Problem)

Problem: Square extends Rectangle 
class Rectangle {
    protected int width;
    protected int height;

    public void setWidth(int width) {
        this.width = width;
    }

    public void setHeight(int height) {
        this.height = height;
    }

    public int getArea() {
        return width * height;
    }
}
    
class Square extends Rectangle {

    @Override
    public void setWidth(int width) {
        this.width = width;
        this.height = width;
    }

    @Override
    public void setHeight(int height) {
        this.height = height;
        this.width = height;
    }
}

Why this breaks LSP:

  • Rectangle allows width and height to change independently
  • Square forces width = height
  • Methods expecting Rectangle get unexpected behavior
  • Subclass changes the contract of the parent

4. LSP Compliant Design (Correct Way)

Solution: Avoid incorrect inheritance

Use a Common Abstraction

interface Shape {
    int getArea();
}
    
class Rectangle implements Shape {
    private int width;
    private int height;

    public Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    public int getArea() {
        return width * height;
    }
}
    
class Square implements Shape {
    private int side;

    public Square(int side) {
        this.side = side;
    }

    public int getArea() {
        return side * side;
    }
}

Both classes now follow the same contract without breaking expectations.

5. Real-World LSP Violation Example

Example: Bird → Penguin 
class Bird {
    public void fly() {
        // flying logic
    }
}

class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("Penguins cannot fly");
    }
}

Penguin cannot substitute Bird safely because it breaks expected behavior.

6. Correct Design for Bird Example

Solution: Separate behaviors 
interface Bird {
    void eat();
}

interface FlyingBird extends Bird {
    void fly();
}
    
class Sparrow implements FlyingBird {
    public void eat() {}
    public void fly() {}
}

class Penguin implements Bird {
    public void eat() {}
}

7. LSP in Spring Boot (Practical View)

public interface PaymentService {
    void pay();
}
    
@Service
public class UPIPaymentService implements PaymentService {
    public void pay() {
        // upi logic
    }
}

@Service
public class CardPaymentService implements PaymentService {
    public void pay() {
        // card logic
    }
}

Any implementation can replace another without breaking behavior. Spring’s dependency injection relies heavily on LSP.

8. Common Mistakes with LSP

  • Using inheritance just to reuse code
  • Throwing unsupported exceptions in subclasses
  • Strengthening preconditions in child classes
  • Weakening postconditions
Rule of thumb:
If a subclass surprises the caller → inheritance is wrong.

9. Interview-Ready Summary

The Liskov Substitution Principle ensures that subclasses remain true to the behavior promised by their parent classes. If a subclass cannot honor that contract, inheritance should be avoided.

10. One-Line Memory Hook

“If the child cannot fully behave like the parent, don’t use inheritance.”
