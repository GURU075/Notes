SOLID Principles – Complete Interview & Practical Guide

This document explains all five SOLID principles with clear reasoning, bad vs good examples, and interview-ready summaries.

1. Single Responsibility Principle (SRP)

Definition

A class should have only one reason to change — it should do only one job.

Why SRP Exists

  • Reduces complexity
  • Makes testing easier
  • Limits impact of change

Violation Example

class UserService { void login() {} void sendEmail() {} void generateReport() {} }

Correct Design

class AuthService { void login() {} } class EmailService { void sendEmail() {} } class ReportService { void generateReport() {} }
Interview Summary: SRP keeps classes focused and reduces the risk of breaking unrelated behavior.

2. Open–Closed Principle (OCP)

Definition

Software entities should be open for extension but closed for modification.

Why OCP Exists

  • Prevents regression bugs
  • Protects stable code
  • Enables safe feature growth

Violation Example

class PaymentService { void pay(String type) { if (type.equals("CARD")) {} else if (type.equals("UPI")) {} } }

Correct Design

interface PaymentMethod { void pay(); } class CardPayment implements PaymentMethod { public void pay() {} } class UPIPayment implements PaymentMethod { public void pay() {} }
Interview Summary: New behavior should be added by extending the system, not by changing existing code.

3. Liskov Substitution Principle (LSP)

Definition

Subclasses must be substitutable for their base classes without breaking behavior.

Why LSP Exists

  • Ensures safe polymorphism
  • Avoids unexpected side effects

Violation Example

class Rectangle { void setWidth(int w) {} void setHeight(int h) {} } class Square extends Rectangle { // Forces width = height }

Correct Design

interface Shape { int area(); } class Rectangle implements Shape { public int area() { return 0; } } class Square implements Shape { public int area() { return 0; } }
Interview Summary: If a child class changes expected parent behavior, LSP is violated.

4. Interface Segregation Principle (ISP)

Definition

Clients should not be forced to depend on interfaces they do not use.

Why ISP Exists

  • Avoids empty method implementations
  • Improves flexibility
  • Reduces ripple effects of change

Violation Example

interface Machine { void print(); void scan(); void fax(); }

Correct Design

interface Printer { void print(); } interface Scanner { void scan(); } interface Fax { void fax(); }
Interview Summary: Prefer small, focused interfaces over large, generic ones.

5. Dependency Inversion Principle (DIP)

Definition

High-level modules should not depend on low-level modules; both should depend on abstractions.

Why DIP Exists

  • Reduces tight coupling
  • Improves testability
  • Makes implementations replaceable

Violation Example

class OrderService { MySQLDatabase db = new MySQLDatabase(); }

Correct Design

interface Database {} class MySQLDatabase implements Database {} class OrderService { Database db; }
Interview Summary: Depend on interfaces, not concrete classes. Dependency Injection implements DIP.

Final One-Line SOLID Summary

  • SRP: One class → one responsibility
  • OCP: Extend, don’t modify
  • LSP: Child must fully behave like parent
  • ISP: No forced unused methods
  • DIP: Depend on abstractions
