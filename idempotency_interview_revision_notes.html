Idempotency — Interview Revision Notes

Quick memory map for REST API, Microservices, Payments, Kafka, and Retry handling.

REST API HTTP Methods Microservices Kafka Payment API Retry Safety

1. One-Line Definition

Idempotency means performing the same operation multiple times should produce the same final result as performing it once.

Same request repeated → Same final state → No duplicate side effect

2. Mind Map

IDEMPOTENCY Retry-safe operation
Meaning Same request multiple times gives same final result.
Why Needed? Network timeout, double click, retry, server crash, message redelivery.
Where Used? REST API, Microservices, Payments, Kafka, Queues, Distributed Systems.
HTTP Methods GET, PUT, DELETE are idempotent. POST is usually not.
Problem Duplicate order, duplicate payment, duplicate invoice, duplicate DB insert.
Solution Idempotency key, eventId, request hash, unique DB constraint, Redis/DB storage.

3. HTTP Methods Revision

Method Idempotent? Reason
GET Yes Only reads data. Repeating it does not change server state.
PUT Yes Updates/replaces resource to a fixed final state.
DELETE Yes After first delete, resource is gone. Repeated calls keep it gone.
POST No Usually creates a new resource every time.
PATCH Depends Setting city=Pune is idempotent. incrementBalanceBy=100 is not.

4. Memory Trick

GPD are idempotent:

G = GET
P = PUT
D = DELETE

POST is not idempotent by default. PATCH depends on implementation.

5. Safe vs Idempotent

Concept Meaning
Safe Does not modify server data.
Idempotent Repeated calls produce same final state.
Important: All safe methods are idempotent, but all idempotent methods are not safe.

6. Simple Examples

Idempotent

PUT /users/101 { "name": "Rahul" }

Call 1 time or 5 times, final name remains Rahul.

Not Idempotent

POST /orders { "productId": 10 }

Call 5 times, 5 new orders may get created.

7. Idempotency Key

An Idempotency Key is a unique key sent by the client to identify one unique operation.

POST /payments Idempotency-Key: PAY_ORD_1001 { "orderId": "ORD1001", "amount": 500 }
1
Client sends request with Idempotency-Key.
2
Server checks whether this key already exists in DB/Redis.
3
If key does not exist, server processes the request and stores the response.
4
If same key comes again, server does not process again.
5
Server returns the previous saved response.

8. What to Store?

Field Purpose
idempotency_key Unique request identifier
request_hash Prevents same key being reused with different request body
status PROCESSING, SUCCESS, FAILED
response_body Return same response for duplicate request
created_at Used for expiry/cleanup

9. Request Hash Rule

Same key + same body
Return old response.
Same key + different body
Reject request because same key is being misused.
Idempotency-Key: abc-123 First body: amount = 500 Second body: amount = 1000 Result: Error / Conflict

10. Payment API Example

Problem: Payment is successful, but response timeout happens. Client retries.

  • Without idempotency: amount may be deducted twice.
  • With idempotency: amount is deducted only once.
  • Retry returns old successful response.
Order Service → Payment Service Same Idempotency-Key: PAY_ORD_1001 First call → process payment Retry call → return old response

11. Kafka / Queue Example

Kafka usually provides at-least-once delivery, so the same message can be consumed more than once.

Message: { "eventId": "EVT1001", "orderId": "ORD1001", "status": "PAID" }
  • If eventId already processed → skip.
  • If eventId not processed → process and save eventId.
  • This is called an Idempotent Consumer.

12. Idempotency vs Related Concepts

Concept Meaning Example
Idempotency Same request repeated should have same final result. Same payment retry should not deduct twice.
Retry Calling operation again after timeout/failure. Order service retries payment call.
Deduplication Detect duplicate request/message and ignore it. Skip already processed eventId.
Concurrency Multiple requests at the same time. Two users booking same seat.

13. Implementation Options

  • Idempotency Key: best for POST APIs like payment/order creation.
  • Unique DB constraint: prevents duplicate row for same orderId/eventId.
  • Processed event table: best for Kafka consumers.
  • Redis: useful for fast temporary key storage.
  • Request hash: validates same key is used for same request body.

14. Common Mistakes

  • Thinking idempotency means same response every time. Actually, same final state matters.
  • Thinking DELETE is not idempotent because second call may return 404.
  • Making payment POST API without idempotency key.
  • Not adding unique constraint on idempotency key/eventId.
  • Not handling PROCESSING state for duplicate in-flight requests.

15. Best Interview Answer

Answer:
Idempotency means executing the same operation multiple times should have the same final result as executing it once. It is very important in REST APIs, microservices, payments, and Kafka because retries can happen due to network timeout or service failure. GET, PUT, and DELETE are idempotent by nature. POST is usually not idempotent, but we can make it idempotent using an Idempotency-Key. For Kafka consumers, we can store processed event IDs to avoid duplicate message processing.

16. Quick Interview Questions

Q1. What is idempotency?

Same request repeated multiple times should produce the same final result as one request.

Q2. Which HTTP methods are idempotent?

GET, PUT, DELETE. PATCH depends. POST is usually not idempotent.

Q3. Is DELETE idempotent?

Yes. First call may delete resource. Second call may return 404, but final state is same: resource does not exist.

Q4. How to make POST idempotent?

Use Idempotency-Key and store key, request hash, status, and response in DB/Redis.

Q5. How to make Kafka consumer idempotent?

Store processed eventId/messageId. If same event comes again, skip processing.
